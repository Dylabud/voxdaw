## Completed Steps Log

* **[2026-07-10] Phase 146b — Stacked-Point Tempo Steps: Epsilon-Separated bpm Events (`tempoMath.js` + tests, `useWorkstationAudio.js`, `audioBounce.js`):**

  The Phase 146 crash persisted in one configuration Dylan isolated: **two tempo-lane points stacked at the same measure plus a point ramping into them.** Root cause (Tone 15.1.22 `TickParam.getTimeOfTick`): our step idiom scheduled `ramp(b1, T)` + `set(b2, T)` at the SAME timestamp — the tick↔time quadratic inversion resolves the ramp's endpoint via `getValueAtTime(after.time)`, and `Timeline.get` is last-wins, so it solved against the POST-step value `b2` instead of the ramp's true target `b1`; a downward step turns the discriminant negative → `sqrt(NaN)` → NaN tick time → the same `getTicksAtTime` "reading 'time' of undefined" crash. The quadratic branch requires `before.value !== after.value` (a non-flat ramp INTO the step), which is exactly why placing a point before the stack was part of the repro and deleting one twin masked it. Same latent hazard: the re-anchor `set` at `audioNow` shared `cancelAndHoldAtTime`'s internal ramp+set pair timestamp. **Fix — invariant: never two differing-value bpm events at one timestamp** (Transport.bpm only; ordinary Params don't integrate ticks). New pure `tempoScheduleOps(map, nowM, baseTime, eps = TEMPO_STEP_EPS = 1e-3)` in `tempoMath.js` (replaces the duplicated live/offline anchor loops; 4 new Jest tests incl. the repro shape) emits strictly-increasing event times: ramp to the FIRST stacked value at its true time (follows the drawn line, per Dylan), then `set` each subsequent value 1 ms later — inaudible for tempo, ≫ Tone's 1e-6 EQ tolerance; the leading re-anchor set sits at `baseTime + eps`. Stacked points remain fully supported in the lane; no data changes. Critique of Gemini: the "sort + jump instead of ramp" compiler logic he proposed already existed — the missing piece was that on `Transport.bpm` even a JUMP sharing a ramp's end **timestamp** trips Tone's tick inversion; the fix is timestamp separation, not op-kind selection. Follow-up UX fix (same day): `previewTempo` is now gated to a non-running transport — while playing, holding/dragging a tempo point used to pull the LIVE tempo to the held value; the playing curve now only updates on the mouseup commit (paused/stopped preview unchanged).

* **[2026-06-02] Phase 141 — Zoom Anchor Jump Fix (batching-independent anchor) (`WorkstationShell.jsx`):**
  Long-standing bug: zooming in/out **fast** jerked the region/measure under the cursor right (in) / left (out) — worse far down the timeline, worse with a lot to render, worse while playing. Root cause was a **stale-read in the anchor math**, not a React-speed problem: the wheel handler computed `absoluteX = mouseX + el.scrollLeft`, but the scroll correction is applied later in a `useLayoutEffect` after React commits. When wheel events outrun commits (exactly when there's a lot to render), React batches them, so every batched event reads the **same stale `el.scrollLeft`** and the final `pendingScrollRef` came from only the **last step's** `next/prev` ratio instead of the full committed→final zoom. Error scaled with `absoluteX` (worse far right) and render latency (worse with many regions / live playhead).

  Fix: chain the zoom across batched events via `liveZoomRef` (committed `zoomLevel` lags during a gesture), and chain the scroll anchor via the existing `pendingScrollRef` — the base scroll is `pendingScrollRef.current ?? el.scrollLeft` (the in-flight target while a correction is pending, else the real DOM scroll when idle). Both wheel handlers compute a right-edge-clamped `nextScroll`, set the pending-scroll refs, and `setZoomLevel(nextZoom)` directly; `liveZoomRef` is kept in sync in the ResizeObserver min-zoom clamp. Everything else — the deferred `useLayoutEffect` scroll application, `drawTimelineGrid`, regions, ruler, playhead rAF, scroll-sync — is **untouched**, so the Phase 137-138 grid is unaffected. Under extreme load the zoom may step coarsely but the cursor anchor is always preserved (never jumps away).

  **(Corrected after a regression.)** The first attempt added a separate `liveScrollRef` reconciled in the scroll handlers (`liveScrollRef = e.target.scrollLeft`); each programmatic correction's native `scroll` event overwrote it with the committed-state (lagging) scroll, desyncing it from `liveZoomRef` → violent rubber-banding, even on empty projects. The fix was to delete `liveScrollRef` entirely and use `pendingScrollRef` (already the source of truth for the correction) as the anchor base, with `el.scrollLeft` as the idle fallback — no scroll-event reconciliation, so no feedback loop, and manual scrolls are captured for free.
